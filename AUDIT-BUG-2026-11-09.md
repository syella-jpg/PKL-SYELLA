# Audit sistem Laporan Korporat — 9 November 2026

Audit kode dan pengujian lokal, tanpa memperbaiki fitur yang sedang dikunci. Tidak ada nilai keuangan atau nama produk dari raw data yang disalin ke dokumen ini. Semua reproduksi tambahan memakai data sintetis atau database double; tidak ada penulisan ke database produksi.

## Kesimpulan

Ada bug nyata pada kontrol akses, pergantian tahun, penghapusan data, rumus template, dan pembacaan ulang data. Keberhasilan tes yang tersedia belum berarti seluruh kondisi pemakaian sudah aman. Temuan di bawah dibedakan antara bug yang direproduksi, ketidaksesuaian alur yang terlihat langsung dari kode, dan risiko instalasi.

## F01 — Identitas pengguna browser bukan autentikasi server

Lokasi: `login/login.html:237`, `dashboard/tm_bod_content_api.php:35`, `dashboard/analysis_api.php:57`, `dashboard/analysis_locks_api.php:15`, `upload/upload.php:71`, `api/report.php:24`.

Login umum memeriksa akun di JavaScript dan menyimpan identitas di sessionStorage. Handler penyimpanan isi TM BOD menerima nama pengguna dari JSON dan cukup memeriksa apakah namanya masuk daftar. Tidak ada verifikasi sesi server atau token autentikasi pada handler itu. Endpoint upload dan sejumlah endpoint baca juga tidak menerapkan autentikasi bersama. Token untuk transfer analisis admin 1 pada endpoint tersendiri belum melindungi seluruh API.

Bukti: handler TM BOD yang sebenarnya dieksekusi dengan koneksi pengganti. Permintaan tanpa sesi/token diterima dan menjalankan penyimpanan pada double. Tidak ada database produksi yang disentuh.

Dampak: pihak yang dapat menjangkau API bisa melewati pembatasan halaman login pada endpoint yang tidak dilindungi. Ini bukan bukti bahwa kebocoran sudah terjadi. CORS tidak menggantikan autentikasi server.

Perbaikan yang disarankan: autentikasi dan pemeriksaan peran bersama di server untuk endpoint baca/tulis, identitas pencatat perubahan berasal dari sesi yang sudah diverifikasi, serta akun/password dikelola di server. Pertahankan alur login antarmuka yang sudah ada sejauh memungkinkan.

## F02 — Unduhan BOD MNJ dapat berhasil dengan data bawaan saat database gagal

Lokasi: `dashboard/report-templates.js:178–189`.

`readYear` menyiapkan file bawaan 2025/2026, lalu menangkap semua kegagalan request API dan melanjutkan dengan file bawaan. Penolakan jaringan, HTTP 500, dan tidak adanya unggahan diperlakukan dengan cara yang sama. Pemberitahuan hanya masuk console.

Bukti: fetch dibuat gagal; pemanggilan `replaceBodMnjTemplateSheet` tetap selesai dan membentuk sheet BOD MNJ dari file bawaan.

Dampak: laporan terlihat berhasil dibuat, tetapi bisa tidak memakai unggahan admin terbaru. Bukan bukti bahwa data produksi saat ini sudah salah.

Perbaikan: bedakan respons sukses tanpa data dengan kegagalan koneksi/server. Kegagalan server seharusnya menghentikan bagian laporan yang bergantung pada data itu atau memperlihatkan status sumber yang jelas; jangan diam-diam mengganti sumber.

## F03 — Ethical belum sepenuhnya fleksibel setelah 2026

Lokasi: `dashboard/report-templates.js:201–202`, `dashboard/report-templates.js:276`, `includes/bod_mnj_workbook.php:411`.

Pengisian biaya Ethical dipanggil untuk 2025 dan 2026 saja. Penyegaran TOTAL ETHICAL pada blok MCM juga mengulangi daftar tahun tetap `[2025,2026]` pada JavaScript dan PHP.

Bukti: workbook sintetis berisi Revenue 100, Biaya 30, dan MCM lama 999. Untuk 2026 MCM berubah menjadi 70; untuk 2027 nilai lama tetap bertahan. Semua angka ini sintetis.

Dampak: meskipun menu periode sudah menampilkan tahun baru, sebagian hasil Ethical dapat kosong atau tidak diperbarui pada 2027 dan selanjutnya.

Perbaikan: tentukan tahun dari periode dan judul blok yang benar-benar tersedia. Uji setidaknya pasangan 2026/2027 dan 2027/2028 untuk browser serta pembuat workbook PHP.

## F04 — Penghapusan ROD tidak selalu diteruskan ke database

Lokasi: `includes/bod_kx_sell_in_input_store.php:41–59`, `includes/bod_kx_sell_in_input_store.php:75–88`.

Penggabungan mempertahankan record lama dan hanya menandai kelompok/bulan sebagai diganti jika ada nilai non-null pada input baru. Jika seluruh produk ROD kelompok itu dihapus, kelompok tersebut tidak masuk daftar perubahan. Penghapusan satu produk juga dapat menyisakan bulan lama yang tidak tersentuh oleh produk lain.

Bukti: state lama berisi satu produk ROD GB 1. Template gabungan baru tidak lagi memiliki produk ROD itu dan masih memiliki isian PENJUALAN yang valid. Hasil merge tetap menyimpan produk lama dan tidak menghasilkan perubahan target untuk dihapus.

Dampak: template yang barisnya telah dihapus dapat berbeda dari target laporan. Ini adalah kondisi tepi yang direproduksi; tidak menyatakan kasus raw data pengguna sebelumnya disebabkan bug ini.

Perbaikan: bedakan unggahan bulanan parsial dengan unggahan template gabungan yang menyatakan susunan produk lengkap. Sertakan penanda eksplisit kelompok/bulan yang dihapus, lalu perbarui rincian dan agregat dalam satu transaksi. Nilai kosong yang berarti belum tersedia tetap harus dibedakan dari penghapusan dan nol.

**Status perbaikan F04:** diperbaiki setelah audit, atas instruksi pengguna. Template gabungan yang lolos validasi sekarang menyatakan daftar produk ROD yang masih ada. Produk yang dihapus dibuang dari rincian tersimpan; jika kelompok menjadi kosong, seluruh target Januari–Desember kelompok tersebut dihapus dalam transaksi yang sama. Unggahan bulanan parsial tetap mempertahankan ROD. File yang kosong seluruhnya hanya diterima jika benar-benar menghapus ROD tersimpan; kosong tanpa penghapusan tetap ditolak.

Verifikasi tambahan: upload handler sebenarnya diuji dengan XLSX/ODS dan database double untuk penghapusan kelompok terakhir, penghapusan produk dengan bulan berbeda, unduhan berikutnya, unggah ulang, isolasi kelompok/tahun/penjualan, serta rollback ketika penyimpanan rincian gagal. Tes pembaca ROD asli, penjualan bulanan, pengisian laporan dan jenis upload juga lulus. Tidak ada data produksi yang dihapus otomatis; perubahan diterapkan saat pengguna mengunggah kembali template yang sudah diedit. Temuan lain tetap belum diperbaiki.

## F05 — Baris tambahan pada kategori kosong tidak ikut subtotal spreadsheet

Lokasi: `includes/target_revenue_input_template.php:46–59`.

Kategori yang tidak mempunyai produk menghasilkan subtotal `=0`. Ketika pengguna menyisipkan baris sebelum subtotal dan mengisi produk, rumus itu tetap `=0`, karena tidak mempunyai referensi rentang yang bisa bergeser.

Bukti: template September tanpa histori, satu baris disisipkan pada kategori A dan diisi angka sintetis 5. Subtotal spreadsheet tetap 0, sedangkan parser server menghitung 5 dari rincian produk.

Dampak: angka yang terlihat di raw template bisa berbeda dari hasil upload, walaupun kalkulasi server dari rincian produknya benar.

Perbaikan: sediakan mekanisme rentang subtotal yang tetap mencakup baris pertama yang ditambahkan, tanpa mengembalikan banyak baris kosong. Uji kondisi kategori kosong, tambah satu produk, hapus produk terakhir, dan buka ulang XLSX/ODS.

## F06 — Permintaan baca terbaru masih dapat memakai cache

Lokasi: `dashboard/report-api-cache.js:42–55`.

Wrapper fetch mengecualikan `cache: 'reload'` dan request dengan signal dari cache, tetapi tidak mengecualikan `cache: 'no-store'`. Banyak pembaca laporan justru menggunakan no-store. Respons tersimpan mempunyai TTL lima menit.

Bukti: dua fetch sintetis berurutan dengan no-store hanya memanggil jaringan sekali.

Dampak: request yang secara eksplisit menghendaki data terbaru masih bisa menerima data lama. Invalidation upload lokal membantu, tetapi perubahan dari perangkat lain tidak menghasilkan revision lokal yang sama. Selain itu, cache workbook grafik pada halaman Selling Out hanya mendengarkan key target/processed, sedangkan wrapper upload menerbitkan key `konimex_report_revision`; jalur template yang tidak menerbitkan key target/processed perlu diuji juga.

Perbaikan: hormati no-store/no-cache sesuai kebutuhan pemanggil dan satukan invalidation cache API serta workbook grafik. Uji upload pada tab lain dan perubahan dari sesi/perangkat lain.

## F07 — Batas ukuran file tidak konsisten

Lokasi: `upload/page.html:203`, `upload/page.html:250`, `dashboard/unit_sell_out_targets_api.php:19`.

UI dan validasi awal mengiklankan/mengizinkan 50 MB, tetapi TARGET UNIT SELL OUT ditolak backend setelah 8 MB.

Dampak: pengguna dapat memilih file yang dianggap valid oleh halaman, lalu baru mendapat kegagalan saat upload.

Catatan lingkungan: PHP CLI pada audit ini menunjukkan upload_max_filesize dan post_max_size 40M. Ini belum membuktikan konfigurasi PHP HTTP/deployment sama; batas HTTP harus diperiksa terpisah.

Perbaikan: batas per bagian ditampilkan sesuai backend dan diselaraskan dengan konfigurasi server yang benar-benar menjalankan request.

## F08 — Pilihan bagian upload yang belum didukung masih bisa dipilih

Lokasi: `upload/page.html:151–164`, `upload/page.html:1059`, `upload/upload.php:73–83`.

Pilihan seperti DAFTAR, LAUNCH, BOD JML SDM, BOD BI. Opr, dan kelompok UPB muncul di pemilih bagian. Tidak ada cabang pemrosesannya pada halaman maupun pemetaan `$reportTables` di endpoint upload umum.

Dampak: pilihan tampak tersedia tetapi akhirnya ditolak dengan “Divisi upload tidak valid”. Ini merupakan ketidaksesuaian antarmuka dengan fitur yang masih dalam pembangunan.

Perbaikan: beri status belum tersedia atau nonaktifkan pilihan tersebut sampai pemrosesnya selesai; jangan mengklaim bahwa datanya sudah diproses.

## Risiko tambahan — Persiapan database BOD MNJ pada instalasi baru

Lokasi: `includes/bod_mnj_workbook.php:121`, `includes/bod_mnj_workbook.php:138`.

Penyimpanan menyiapkan `bod_mnj_files` otomatis, tetapi kemudian menjalankan INSERT ke `bod_mnj` tanpa menyiapkan tabel relasional itu. Tidak ditemukan CREATE TABLE untuk tabel tersebut dalam kode aplikasi saat audit. Ini akan gagal pada database baru yang tabelnya belum disiapkan terpisah. Tidak ada bukti bahwa tabel pada instalasi pengguna saat ini hilang.

Saran: tetapkan prosedur bootstrap/migrasi yang dapat dijalankan ulang, lalu uji database benar-benar kosong secara terisolasi.

## Pengujian dan batas audit

- 63 file PHP aplikasi: pemeriksaan sintaks lulus.
- 12 halaman HTML: 11 blok JavaScript inline diperiksa; sintaks lulus.
- 34 file JavaScript terpisah: sintaks lulus.
- 109 skrip tes PHP/Node diperiksa. Jalur pemanggilan pertama lulus 99 skrip. Empat tes yang membutuhkan argumen file atau input stdin kemudian dijalankan dengan benar dan lulus, sehingga total akhir 103 lulus.
- Lima tes belum cocok dengan implementasi/harness terkini: `test-dashboard-cache.cjs` (ekstraksi fungsi lama), `test-mtm-appendix.cjs` (pencocokan literal source lama), `test-report-rollover.cjs` (dependensi replaceMtmAppendices belum dimuat), `test-tm-bod-preview.cjs` (DOM double tidak menyediakan classList.toggle), dan `test-unit-revenue-ethical-manual.php` (fixture menulis posisi baris format template lama). Hasil gagal ini tidak langsung dihitung sebagai lima bug aplikasi.
- `test-bod-kx-input-template.php` melewati batas 150 detik pada audit berbarengan. Belum ditentukan apakah ini masalah kinerja aplikasi atau beban skrip tes; tidak dinyatakan sebagai kegagalan kalkulasi.
- Reproduksi tambahan membuktikan F01–F06 secara terpisah memakai input sintetis; F07–F08 ditelusuri dari alur kode.
- Pengujian browser interaktif, beban banyak pengguna, konfigurasi HTTP server aktual, dan seluruh jalur deployment TiDB/Vercel belum dicakup. Audit ini tidak menjamin tidak ada bug lain.
- Kode aplikasi, raw data, dan database produksi tidak diubah. Dokumen audit ini adalah satu-satunya tambahan pada repository.

## Urutan penanganan

1. Tutup akses API tanpa autentikasi server (F01).
2. Hentikan penggantian data diam-diam dan pastikan penghapusan data diterapkan (F02, F04).
3. Perbaiki pergantian tahun dan ketepatan subtotal template (F03, F05).
4. Selaraskan pembacaan ulang/cache, batas upload, dan pilihan bagian yang tersedia (F06–F08).
5. Perbarui tes yang tertinggal dan uji integrasi browser serta database kosong sebelum melanjutkan fitur baru.
